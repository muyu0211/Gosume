# Gosume 开发文档编写规范

本 Skill 统一当前项目（Gosume）所有**开发相关文档**的框架与要素，保证跨迭代/跨需求的一致性与可追溯性。立项出文档时必须调用本 Skill。

## 何时调用

- 一个新需求开始立项，需要产出**需求文档（PRD）**；
- 需求确认后，需要产出**开发方案文档（Dev Plan）**；
- 需要在 `docs/` 下新建/重写任一开发文档；
- 需要审查既有文档是否遵循本规范。

## 核心原则

1. **一文一类**：每个文档要么是「需求文档」，要么是「开发方案文档」，不可混搭。两文通过 `上游/配套` 互链。
2. **先需求后方案**：大需求先出 PRD 定「做什么」，产品/研发确认后再出开发方案定「怎么做」。小改动可只写开发方案，但必须在头部注明上游上下文。
3. **目录归属**：文档放在 `docs/{迭代或主题}/` 子目录下；同一主题的需求 + 方案放同一目录，用文件名区分。本项目目录命名惯例：`Gosume{主题/期数}需求`、`Gosume{二期改造/三期改造}` 等。
4. **命名规范**：文件名建议 `{主题}-{PRD|开发方案}.md`；同一主题多文档时用序号/关键词前缀区分。避免 `PRD.md` 单一靠目录区分的歧义（既有 `docs/Gosume主题需求/PRD.md` 类可保留，但新文档遵循更明确命名）。
5. **决策留痕**：所有已确认的关键决策以「决策记录表」形式写进文档，注明「已确认」，避免返工。
6. **脱敏**：文档正文不得出现账号/密钥/内部 URL/个人数据；示例用占位符（如 `sk-****1234`）。
7. **代码引用**：涉及既有实现一律给出**文件路径 + 关键符号**（函数/结构体/服务方法），便于落地时快速定位。

## 文档头（两文通用）

每个文档顶部放一段引用块元信息，格式：

```
> 版本：v1.0 · 状态：待评审 / 待实施 / 已实施
> 日期：YYYY-MM-DD
> 位置：docs/{目录}/{文件名}.md
> 上游关联：docs/{…}/…PRD.md（需求文档）；配套开发方案/需求文档互链（方案文档）
```

「版本」在每次实质修改后递增；「状态」在流程推进时更新（待评审 → 待实施 → 已实施）。

## 一、需求文档（PRD）结构

按以下章节顺序撰写。**可合并可省略**「现状分析（简单需求）」与「里程碑（单期小需求）」，但灰色标题必须保留骨架。

| 序号 | 章节 | 必填 | 说明 |
|----|------|------|------|
| 1 | 文档信息表 | ✅ | 需求点 / 所属方向 / 优先级 / 版本 / 日期 / 状态 / 总览文档 |
| 2 | 需求概述 | ✅ | 一句话说完做什么、给谁用、解决什么痛点 |
| 3 | 需求背景 | ✅ | 痛点/现状，为什么此时做；尽量带数据或用户场景 |
| 4 | 需求目标 | ✅ | 分条列出可验证的目标；紧跟「非目标/不在范围」，划清边界 |
| 5 | 现状分析（关键约束） | 可选 | 表格式：维度 / 现状 / 约束。有强约束时必须写 |
| 6 | 术语与定义 | 可选 | 术语表；有专有名词时必写 |
| 7 | 范围（In/Out Scope） | ✅ | In：本期做；Out：本期不做（明确原因或拆分到哪期） |
| 8 | 用户故事与需求点 | ✅ | 见下「需求点编号」 |
| 9 | 功能需求 | ✅ | `F1/F2…` 分条，细到可评审、可开发 |
| 10 | 非功能需求 | 可选 | 性能 / 安全 / 兼容 / 离线 / 国际化等分条 |
| 11 | 交付物 | ✅ | 前端 / 后端 / 文档等交付物清单 |
| 12 | 验收标准 | ✅ | 可勾选清单，逐条可测、可回归 |
| 13 | 里程碑（可选） | 可选 | 大需求拆分 M1/M2…，含内容与验收门槛 |
| 14 | 技术方案提示（可选） | 可选 | 给实现的初步倾向 + 项目内可复用资产 + 建议先做的梳理 |
| 15 | 风险与开放问题 | ✅ | 表格：风险/问题 / 说明 / 应对 |

**需求点编号约定**：`PR-xxx`（P=必须发布门槛 / S=应该 / C=可选），每条后附一句期望行为 + 两三条可验收的子要点，并在 §10 验收标准中引用编号。优先级在开头用 `【P】【S】【C】` 标注。

**优先级字段规范**：P0（最高，阻塞发布）/ P1（高）/ P2（中）/ P3（低）。

## 二、开发方案文档（Dev Plan）结构

以 `docs/Gosume接入AI需求/AI接入开发方案.md` 为范本，按以下章节顺序。

| 序号 | 章节 | 必填 | 说明 |
|----|------|------|------|
| 0 | Title | ✅ | `# Gosume {主题} — {子主题} · 开发方案` |
| 1 | 背景与目标 | ✅ | 一句话背景 + 本阶段**只做什么 / 不做什么**；明确「配置+入口」性质的阶段边界 |
| 2 | 已确认的关键决策 | ✅ | 决策表格：决策点 / 结论。来自上游 PRD 或方案评审 |
| 3 | 总体架构 | ✅ | ASCII 图展示前后端数据流与分层归属，标注复用对象 |
| 4 | 后端改动（文件级） | ✅ | 见下「改动表述规范」，含数据模型/新增包/新增服务 |
| 5 | 前端改动（文件级） | ✅ | 见下「前端改动规范」，含服务封装/组件核对/区块结构/校验/样式动画/i18n |
| 6 | 安全约定 | ✅ | 敏感信息存储（如 0600 明文文件）、日志/回显脱敏策略 |
| 7 | 分阶段计划 | ✅ | Phase 表：阶段 / 内容，标注「本次」与「后续」 |
| 8 | 验收要点 | ✅ | 可勾选清单，聚焦可验证行为（重启生效、错误原因、脱敏、数据随迁） |
| 9 | 风险与注意事项 | ✅ | 表格式风险 + 应对/专项验证 |
| 10 | 决策记录 / 实施记录 | 可选 | 大迭代补「决策记录表 + 实施记录」（已实现/已做/验证/deviation） |

### 后端改动表述规范

- 每个改动点给出**文件路径** + **新增/修改/删除**标注 + 关键代码骨架（结构体/函数签名/方法注释）。
- 新增包按职责列文件清单表（文件 / 职责）。
- 数据模型 / DTO 给出完整类型定义与 json tag。
- 新增服务遵循项目 Wails 服务规范：`ServiceName()`、导出方法表（方法 / 说明）、错误处理用 `util/error.go` 的 `UserMsg/UserWrap` 返回中文用户友好消息 + `util.DoRsp` 统一响应。
- 装配与迁移：写明在 `pkg/app/app.go` 的注册位置，以及跨数据目录迁移时需加入的迁移清单。

### 前端改动规范

- 服务封装：给出 `frontend/src/services/{x}Service.ts` 中 `callService('XService','Method',...)` 的封装与 TS 类型声明。
- **复用优先**：给出「可复用组件核对」表（需求 / 复用的组件/样式 / 结论「直接复用 / 不复用但内联范式 / 需新增」），强依赖项目既有实现（如 `CustomSelect`、`form-input`、`globals.css` 的 `.form-section`、`Loader2 animate-spin`、`ConfirmDialog`、`Tooltip`）。
- 区块结构：用 ASCII 框示意 UI 布局。
- 校验：给出 react-hook-form + zod schema，错误文案走 `t()`，统一 `extractErrorMessage`。
- 样式/动画：遵循项目工程约定——用主题令牌（`surface-*`/`primary-*`/`bg-elev`/`text-*`）、`animate-page-enter`、`grid-template-rows 0fr→1fr` 折叠动画、按钮 jelly/scale、下拉 `animate-dropdown-enter`。
- i18n：列出新增/改动词条（zh/en），遵循「英文 ≤ 中文 1.5 倍宽度」规范。

## 三、撰写流程

1. **澄清**：先用 `AskUserQuestion` 确认——是哪类文档（PRD/开发方案）？是否有总览/上游文档？优先级与版本？缺口信息不足时不得凭空臆造。
2. **摸底**：用 Grep/Read 核对既有实现与惯例（同一目录是否有 PRD 可互链、项目 `pkg/{app,service,user_config}` 与 `frontend/src/services|lib|components` 的真实命名），引用真实路径。
3. **选型**：本 Skill 仅产出文档，不写实现代码；文档里给出「复用 vs 新建」结论即可，不擅自扩大范围。
4. **产出**：按上文对应章节模板生成，落盘到 `docs/{目录}/`。落盘后**用 NotifyUser 提示用户审阅**。
5. **互链**：PRD 与开发方案通过「上游/配套」字段互相链接；跨期依赖写明引用文档。

## 四、文档质量自检（写完后逐条过）

- [ ] 两文必备章节齐全，可合并章节已标注省略而非消失。
- [ ] 头部版本/日期/状态/位置/上游齐全。
- [ ] 所有文件路径、服务方法名、组件名在代码库中真实存在（已核对）。
- [ ] 无硬编码魔法值/密钥/个人数据，敏感信息已占位。
- [ ] 「关键决策」与「验收要点」可被后续开发直接执行，无需再次决策。
- [ ] 评审、验收、状态更新留痕（待评审 → 已实施）。
