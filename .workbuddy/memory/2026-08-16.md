## 白屏 bug：glob 返回值是冻结的 module 命名空间对象

**现象**：修复 r-contact（glob 路径 `../../` → `../../../`）后，应用重启**白屏**（#root 完全空）。

**根因**：`import.meta.glob` 默认（**不加 `import: 'default'`**）返回的是 **module 命名空间对象**，且被 Vite 编译成 `Object.freeze(...)`。之前 glob 指向空目录（`frontend/templates/` 不存在）→ `buildTemplateMap` 的 for 循环不执行、不触发；改成 `../../../templates/` 匹配到 16 个模板后，`buildTemplateMap` 里 `meta.is_builtin = true` 对**冻结对象赋值**，在 ES module 严格模式下抛 `TypeError: Cannot add property is_builtin, object is not extensible`，模块顶层抛错 → bundle 加载失败 → 白屏。

**修复**：4 个 glob 都加 `import: 'default'`，让值变成可修改的 JSON 对象 / `?raw` 字符串（而非冻结命名空间对象）。dist 从 1.15MB 降到 681KB（不再生成命名空间包装）。

**教训**：
- `import.meta.glob(..., { eager: true })` 默认返回 `{ default: X, ...命名导出 }` 的**冻结** module 命名空间对象；要直接拿 default 导出必须加 `{ import: 'default' }`。对 glob 结果做任何**写操作**（如 `meta.is_builtin = true`）会抛 TypeError。
- rod 的 `page.EvalOnNewDocument(script)` 要传**直接 JS 代码**，不是箭头函数 `() => {...}`（箭头函数只定义不执行，导致"无错误"是假象、误判了方向）。

## PNG 导出空白 bug（双栏页尾 + 深色模板白色条带）

**现象**：① 双栏模板（split/creative）PNG 导出页尾大量空白；② 深色模板（terminal）PNG 导出页顶/页间/页尾有白色空白。

**根因**（都在 `pkg/export/browser.go` 的 `pngContinuousCSSJS` 注入脚本）：
1. 双栏模板 `.resume-container` 是 `display:grid` + `min-height:297mm`（为了让侧栏通高）。PNG 连续渲染脚本只重置了 `.resume-page` 的 `min-height/height`，**没重置 `.resume-container`** → 每页仍被 grid 容器撑到 297mm → 页尾空白。
2. 脚本把页边距从 `.resume-page`（padding）移到 `.resume-pages-wrapper`（padding-top/bottom），但 wrapper 背景是**透明**的（透出 body 白色），深色模板首尾/页间就露出白色条带。

**修复**：`pngContinuousCSSJS` 里 ① 读页面背景色 `cs.backgroundColor`；② 追加 `.resume-container{min-height:0 !important;height:auto !important}`；③ 给 `.resume-pages-wrapper` 加 `background:<pageBg> !important`。

**验证**：rod 构造"分页后" HTML 注入脚本，测量 page 高度从 297mm 收缩到内容高度（300px/120px）、页间 top==上一页 bottom（无空隙）、wrapper 背景变深色 `rgb(13,17,23)`。

**教训**：PNG"连续渲染"（多页拼一张长图）靠注入 CSS 收缩 `.resume-page`，任何在**内层容器**上写 `min-height`（如 grid 双栏通高、单栏全出血）的模板，都必须同步在该脚本里重置，否则收缩失效；首尾/页间空白是"背景色"问题——wrapper 背景要跟随页面背景色，不能依赖透明透出 body。

## 追加：pngContinuousCSSJS 的 JS 字符串被拆行导致 SyntaxError

**现象**：修复后运行时仍报 `PNG导出: 浏览器截图失败: 注入连续渲染 CSS 失败: eval js error: SyntaxError: Invalid or unexpected token`。

**根因**：`pngContinuousCSSJS` 里 `style.textContent = '.resume-page{...}...'` 这段 JS 单引号字符串，被**某格式化工具/IDE 保存时格式化**拆成了多行（CSS 选择器换行+缩进），JS 单引号字符串**不能跨行**（除非 `\` 续行），导致 rod 的 `page.Eval` 抛 SyntaxError。Go 侧 `go build` 仍能过（反引号原始字符串跨行合法），所以编译通过≠JS 合法。

**修复**：用 Python 脚本把 `style.textContent` 从 `start_marker` 到 `}';` 之间整体替换回**单行**字符串，再 `gofmt -w`（gofmt 对字符串字面量不透明、不会拆行，安全）。

**教训**：
- Go 反引号字符串里内嵌 JS/CSS，**单引号字符串必须单行**；排查 `page.Eval` 报 `SyntaxError` 时，用 `sed -n 'N,Mp' file.go | cat -A` 看原始字节（`^I` 是 Tab），或直接 rod 实测注入来验证。
- `go build` 通过只证明 Go 编译合法，**不证明内嵌 JS 合法**；这类"JS 藏在 Go 字符串里"的改动，验证要以"rod 实际 `page.Eval` 注入成功"为准。

## 双栏中间页页尾空白（分页算法 overflow 基线 bug）

**现象**：双栏模板（split/creative）PNG 导出，末页空白已修复，但**中间页**仍有页尾空白；单栏正常。

**根因**（`frontend/src/lib/paginationCore.ts` 的 `overflows`）：双栏 `.resume-container` 有 `min-height:297mm`（为了让侧栏通高），它把 `page.scrollHeight` 的基线**撑到 297mm**。分页算法用 `scrollHeight > offsetHeight` 判断翻页，于是内容没真正填满时 `scrollHeight` 已经是 297mm（=offsetHeight，不 overflow），中间页 main 内容没满就翻页 → 留下页尾空白。单栏 `.resume-container` 无 min-height，scrollHeight 精确反映内容，所以正常。

**修复**：`overflows` 改为双栏时按 **main 壳的实际内容高度**（`measureChildrenHeight` 累加子元素 offsetHeight+margin，加 main 自身 padding）判断，而非 `page.scrollHeight`。新增 `PageCtx.pageHeight`（297mm 像素）。单栏保持原 scrollHeight 判断。

**验证**（rod 实测）：中间页 main 章节 800px 时，`page.scrollHeight`=1123px（被 min-height 撑起，修复前误判"填满"）vs `measureChildrenHeight`=861px（精确，修复后继续放章节直到填满 297mm）。`containerMinH=1122.52px` 证实撑起来源。

**教训**：CSS 的 `min-height`/`min-width` 会污染 `scrollHeight`/`scrollWidth` 的测量基线——凡是"按内容是否填满来分页/测量"的逻辑，不能依赖 `scrollHeight`（会被 min-height 撑起），要测量**子元素总高度**或临时归零 min-height。grid 双栏"侧栏通高"正是靠 min-height 实现，与分页测量天然冲突。

## ⚠️ 修正：上面的"overflow 基线 bug"判断是误判，修复已 revert

**真实结论**（用 http server + rod navigate 跑通真实分页后验证）：`scrollHeight > offsetHeight` 在双栏下**本就等价于"内容 > 297mm"**——因为 `.resume-page` 的 `height:297mm; overflow:hidden` 使 `scrollHeight = max(297mm, 内容高度)`，当内容 <297mm 时 scrollHeight=offsetHeight（不 overflow、继续放），内容 >297mm 时 overflow。所以原来的 scrollHeight 判断**是对的**，我的 `measureChildrenHeight` 修复是多余的，且它累加 margin 时**没处理 margin collapse**（相邻章节 margin-bottom 合并被重复累加），反而让中间页更早翻页、留白更大。已完全 revert（`git diff` 为空）。

**真实数据**（20 job → 3 页，split）：分页后中间页留白仅 **42px**（章节粒度：最后一个放不下的章节高度），PNG 收缩后中间页高度 = 内容（如 1082px），**无空白**。即"中间页页尾空白"本来就是 PNG 收缩（`.resume-container{min-height:0}`）能解决的——42px 留白被收缩掉。

**待确认**：用户反馈"还没解决"，最可能是①运行旧 exe（`gosume.exe` 02:59 旧 / `bin/Gosume.exe` 03:10 新）②特定简历数据（超大章节）③观察的是 PDF/预览而非 PNG。需用户提供具体模板名+简历内容精确复现。

**教训补充**：
- 判断"min-height 是否污染 scrollHeight"不能想当然——`overflow:hidden + 固定 height` 下 `scrollHeight = max(height, 内容)`，此时 `scrollHeight > offsetHeight` **恰好就是**"内容 > height"，没有污染。

## 预览缩放后状态栏与简历间大间隙（transform scale 占位 bug）

**现象**：状态栏"共 N 页"贴底部，缩小简历才出现；缩得越小时，简历末尾与状态栏之间间隙越大。

**根因**（`PreviewPanel.tsx` 原有 bug，非本次改动引入）：缩放用 `transform: scale()`，它只做**视觉缩放、不改变布局占位**。iframe 占位高度始终是原始多页总高 `containerHeight`，缩放容器外层又没做高度补偿，于是状态栏被顶到"原始高度"下方，scale<1 时就空出 `(1-scale)*containerHeight` 的间隙。

**修复**：在缩放内容外再套一层占位容器 `height: containerHeight * scale` + `overflow: hidden`（裁掉 transform 的布局溢出），状态栏放占位容器之后，紧贴缩放后的简历末尾。宽度侧原本就有 `width: pxW*scale` 的补偿，高度侧此前缺失，补上即对称。

**教训**：`transform: scale` 缩放元素时，**布局占位（宽高）不随 scale 变**，任何依赖"缩放后实际尺寸"的兄弟元素排版（如下方状态栏、滚动高度）都要手动按 scale 补偿占位高度/宽度；或用 `zoom`（Chromium 支持、会改变布局）替代。
