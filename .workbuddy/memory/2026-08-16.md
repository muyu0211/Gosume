## 白屏 bug：glob 返回值是冻结的 module 命名空间对象

**现象**：修复 r-contact（glob 路径 `../../` → `../../../`）后，应用重启**白屏**（#root 完全空）。

**根因**：`import.meta.glob` 默认（**不加 `import: 'default'`**）返回的是 **module 命名空间对象**，且被 Vite 编译成 `Object.freeze(...)`。之前 glob 指向空目录（`frontend/templates/` 不存在）→ `buildTemplateMap` 的 for 循环不执行、不触发；改成 `../../../templates/` 匹配到 16 个模板后，`buildTemplateMap` 里 `meta.is_builtin = true` 对**冻结对象赋值**，在 ES module 严格模式下抛 `TypeError: Cannot add property is_builtin, object is not extensible`，模块顶层抛错 → bundle 加载失败 → 白屏。

**修复**：4 个 glob 都加 `import: 'default'`，让值变成可修改的 JSON 对象 / `?raw` 字符串（而非冻结命名空间对象）。dist 从 1.15MB 降到 681KB（不再生成命名空间包装）。

**教训**：
- `import.meta.glob(..., { eager: true })` 默认返回 `{ default: X, ...命名导出 }` 的**冻结** module 命名空间对象；要直接拿 default 导出必须加 `{ import: 'default' }`。对 glob 结果做任何**写操作**（如 `meta.is_builtin = true`）会抛 TypeError。
- rod 的 `page.EvalOnNewDocument(script)` 要传**直接 JS 代码**，不是箭头函数 `() => {...}`（箭头函数只定义不执行，导致"无错误"是假象、误判了方向）。

## PNG 导出空白 bug（双栏页尾 + 深色模板白色条带）

**现象**：① 双栏模板（split/creative）PNG 导出页尾大量空白；② 深色模板（terminal）PNG 导出页顶/页间/页尾有白色空白。

2. 脚本把页边距从 `.resume-page`（padding）移到 `.resume-pages-wrapper`（padding-top/bottom），但 wrapper 背景是**透明**的（透出 body 白色），深色模板首尾/页间就露出白色条带。

**修复**：`pngContinuousCSSJS` 里 ① 读页面背景色 `cs.backgroundColor`；② 追加 `.resume-container{min-height:0 !important;height:auto !important}`；③ 给 `.resume-pages-wrapper` 加 `background:<pageBg> !important`。

**验证**：rod 构造"分页后" HTML 注入脚本，测量 page 高度从 297mm 收缩到内容高度（300px/120px）、页间 top==上一页 bottom（无空隙）、wrapper 背景变深色 `rgb(13,17,23)`。

**教训**：PNG"连续渲染"（多页拼一张长图）靠注入 CSS 收缩 `.resume-page`，任何在**内层容器**上写 `min-height`（如 grid 双栏通高、单栏全出血）的模板，都必须同步在该脚本里重置，否则收缩失效；首尾/页间空白是"背景色"问题——wrapper 背景要跟随页面背景色，不能依赖透明透出 body。

## 追加：pngContinuousCSSJS 的 JS 字符串被拆行导致 SyntaxError

**现象**：修复后运行时仍报 `PNG导出: 浏览器截图失败: 注入连续渲染 CSS 失败: eval js error: SyntaxError: Invalid or unexpected token`。

**根因**：`pngContinuousCSSJS` 里 `style.textContent = '.resume-page{...}...'` 这段 JS 单引号字符串，被**某格式化工具/IDE 保存时格式化**拆成了多行（CSS 选择器换行+缩进），JS 单引号字符串**不能跨行**（除非 `\` 续行），导致 rod 的 `page.Eval` 抛 SyntaxError。Go 侧 `go build` 仍能过（反引号原始字符串跨行合法），所以编译通过≠JS 合法。

**修复**：用 Python 脚本把 `style.textContent` 从 `start_marker` 到 `}';` 之间整体替换回**单行**字符串，再 `gofmt -w`（gofmt 对字符串字面量不透明、不会拆行，安全）。

**教训**：
- Go 反引号字符串里内嵌 JS/CSS，**单引号字符串必须单行**；排查 `page.Eval` 报 `SyntaxError` 时，用 `sed -n 'N,Mp' file.go | cat -A` 看原始字节（`^I` 是 Tab），或直接 rod 实测注入来验证。
- `go build` 通过只证明 Go 编译合法，**不证明内嵌 JS 合法**；这类"JS 藏在 Go 字符串里"的改动，验证要以"rod 实际 `page.Eval` 注入成功"为准。

## 双栏中间页页尾空白（分页算法 overflow 基线 bug）

**现象**：双栏模板（split/creative）PNG 导出，末页空白已修复，但**中间页**仍有页尾空白；单栏正常。

**根因**（`frontend/src/lib/paginationCore.ts` 的 `overflows`）：双栏 `.resume-container` 有 `min-height:297mm`（为了让侧栏通高），它把 `page.scrollHeight` 的基线**撑到 297mm**。分页算法用 `scrollHeight > offsetHeight` 判断翻页，于是内容没真正填满时 `scrollHeight` 已经是 297mm（=offsetHeight，不 overflow），中间页 main 内容没满就翻页 → 留下页尾空白。单栏 `.resume-container` 无 min-height，scrollHeight 精确反映内容，所以正常。

**修复**：`overflows` 改为双栏时按 **main 壳的实际内容高度**（`measureChildrenHeight` 累加子元素 offsetHeight+margin，加 main 自身 padding）判断，而非 `page.scrollHeight`。新增 `PageCtx.pageHeight`（297mm 像素）。单栏保持原 scrollHeight 判断。

**验证**（rod 实测）：中间页 main 章节 800px 时，`page.scrollHeight`=1123px（被 min-height 撑起，修复前误判"填满"）vs `measureChildrenHeight`=861px（精确，修复后继续放章节直到填满 297mm）。`containerMinH=1122.52px` 证实撑起来源。

**教训**：CSS 的 `min-height`/`min-width` 会污染 `scrollHeight`/`scrollWidth` 的测量基线——凡是"按内容是否填满来分页/测量"的逻辑，不能依赖 `scrollHeight`（会被 min-height 撑起），要测量**子元素总高度**或临时归零 min-height。grid 双栏"侧栏通高"正是靠 min-height 实现，与分页测量天然冲突。

## ⚠️ 修正：上面的"overflow 基线 bug"判断是误判，修复已 revert

**真实结论**（用 http server + rod navigate 跑通真实分页后验证）：`scrollHeight > offsetHeight` 在双栏下**本就等价于"内容 > 297mm"**——因为 `.resume-page` 的 `height:297mm; overflow:hidden` 使 `scrollHeight = max(297mm, 内容高度)`，当内容 <297mm 时 scrollHeight=offsetHeight（不 overflow、继续放），内容 >297mm 时 overflow。所以原来的 scrollHeight 判断**是对的**，我的 `measureChildrenHeight` 修复是多余的，且它累加 margin 时**没处理 margin collapse**（相邻章节 margin-bottom 合并被重复累加），反而让中间页更早翻页、留白更大。已完全 revert（`git diff` 为空）。

**真实数据**（20 job → 3 页，split）：分页后中间页留白仅 **42px**（章节粒度：最后一个放不下的章节高度），PNG 收缩后中间页高度 = 内容（如 1082px），**无空白**。即"中间页页尾空白"本来就是 PNG 收缩（`.resume-container{min-height:0}`）能解决的——42px 留白被收缩掉。

**待确认**：用户反馈"还没解决"，最可能是①运行旧 exe（`gosume.exe` 02:59 旧 / `bin/Gosume.exe` 03:10 新）②特定简历数据（超大章节）③观察的是 PDF/预览而非 PNG。需用户提供具体模板名+简历内容精确复现。

**教训补充**：
- 判断"min-height 是否污染 scrollHeight"不能想当然——`overflow:hidden + 固定 height` 下 `scrollHeight = max(height, 内容)`，此时 `scrollHeight > offsetHeight` **恰好就是**"内容 > height"，没有污染。

## 预览缩放后状态栏与简历间大间隙（transform scale 占位 bug）

**现象**：状态栏"共 N 页"贴底部，缩小简历才出现；缩得越小时，简历末尾与状态栏之间间隙越大。

**根因**（`PreviewPanel.tsx` 原有 bug，非本次改动引入）：缩放用 `transform: scale()`，它只做**视觉缩放、不改变布局占位**。iframe 占位高度始终是原始多页总高 `containerHeight`，缩放容器外层又没做高度补偿，于是状态栏被顶到"原始高度"下方，scale<1 时就空出 `(1-scale)*containerHeight` 的间隙。

**修复**：在缩放内容外再套一层占位容器 `height: containerHeight * scale` + `overflow: hidden`（裁掉 transform 的布局溢出），状态栏放占位容器之后，紧贴缩放后的简历末尾。宽度侧原本就有 `width: pxW*scale` 的补偿，高度侧此前缺失，补上即对称。

**教训**：`transform: scale` 缩放元素时，**布局占位（宽高）不随 scale 变**，任何依赖"缩放后实际尺寸"的兄弟元素排版（如下方状态栏、滚动高度）都要手动按 scale 补偿占位高度/宽度；或用 `zoom`（Chromium 支持、会改变布局）替代。

## 新增：删除用户导入的模板（保护内置模板）

**背景**：一期改造全面更新模板后，旧 skill / 旧版 HTML 制作的模板在新 Gosume 中无法正常渲染，需提供删除用户模板的能力，但**不允许删除内置模板**。

**现状排查**：后端**已具备**删除能力——`TemplateService.DeleteTemplate(id)` → `TemplateStore.SoftDelete(id)`，SQL 带 `WHERE is_builtin=0 AND is_deleted=0`，删除内置模板（is_builtin=1）会返回 `TEMPLATE_NOT_FOUND` 错误。缺的只是前端入口。

**改动**：
- `templateService.ts` 加 `deleteTemplate(id)`（仅 Wails 环境，调 `TemplateService.DeleteTemplate`）。
- `TemplateSwitcher.tsx`：模板项从 `<button>` 改为 `<div role="button">`（button 不能嵌套 button），仅 `!tmpl.is_builtin` 显示垃圾桶删除按钮（Loader2 加载态 + `window.confirm` 确认）；删除后刷新列表、缩略图，若删的是当前激活模板则切到列表第一个。
- `WelcomePage.tsx`：`TemplateCard` 加 `onDelete`/`isDeleting` prop，meta 区标题行对用户模板显示删除按钮；主组件 `handleDeleteTemplate` 删除后 `loadData()` 刷新。

**双重保护**：前端用 `!is_builtin` 只渲染删除按钮 + 后端 SQL `is_builtin=0` 条件，两层都阻止删除内置模板。

**构建**：`--emptyOutDir false` 绕过沙箱清 dist，前端构建成功（1868 模块）+ `go build` 新 exe。

## 预览渲染优化：调研 + 开发文档（方案 4 增量 DOM diff）

**背景**：编辑时预览闪烁/跳变、主页进入「突现」，用户选方案 4（增量 DOM diff），要求文档先行。

**调研结论（根因）**：
- 闪烁主因：`PreviewPanel.tsx:33-35` 每次编辑 `doc.open/write/close` 全量重写 iframe（head/CSS 一并重写 → 白屏 + 字体图片重载）。
- 跳变主因：`paginationCore.ts:175` `paginateResume` 用 `body.replaceChildren` 破坏性重建展示 DOM（按测量高度克隆拆分 section 到多页）。
- 放大因素：`usePreview.ts:25` 编辑期间每次重拉 `loadTemplateContent`（后端往返）。
- 突现：进入 `/editor` 时 `previewHtml` 为空 → 占位 → 跑完防抖+渲染+分页后整块冒出。

**关键边界判断**：diff 只能优化「内容层」，**无法消除「分页层」重建**——分页本质是"按高度克隆拆分"，必须重算。分页层闪烁靠「双缓冲 + 节流 + 内容签名跳过」掩盖，非 diff 直接解决。

**产出**：`docs/Gosume预览渲染优化开发方案.md`，方案 = 渲染分层（骨架/内容/展示三层）+ morphdom diff + 骨架缓存 + 分页双缓冲，分 M0(前置核对)/M1(内容 diff)/M2(分页体验)/M3(keyed diff 可选) 四里程碑。

**调研识别的坑（需 M0 核对）**：① morphdom 跨 document（iframe 内解析规避）；② `doc.fonts.ready` 切模板才需重等；③ 后端 Go 字段名须是 `ID`（`{{.ID}}` 在 html/template 未定义会**报错**，非静默空）；④ 分页 memo 签名须纳入布局档位+头像尺寸，不能只看文本；⑤ `paginateResume` 写死 `body.querySelector('.resume-container')`，需加「源容器」参数（默认回退 body 保导出兼容）；⑥ 缩放 transform 下双缓冲坐标一致。

**下一步**：等用户确认文档后进入 M0/M1。

## 头像尺寸调节：保存失败 + slider 固定 100px 修复

**背景**：上一轮加了头像宽高滑块（40–200px）+ 比例预设，但出现两个问题：① 修改尺寸后保存失效/保存失败；② slider 初始值固定 100px，而非简历中头像实际渲染尺寸。

**根因**：
- 保存失效：后端 `pkg/model/personal.go` 的 `Personal` 结构体**缺 `avatar_width`/`avatar_height` 字段**。前端 `EditorPage.handleSave` 调 `SetResume(resume)` 把整个简历传给后端，JSON 反序列化时这两个字段被静默丢弃，SQLite 里没存，重载后丢失。
- slider 固定 100：`PersonalSection` 里 `p.avatar_width ?? 100` 硬编码 100px，但模板头像默认尺寸是 40~57pt（≈53~101px）不等，未读真实渲染值。

**改动**：
- `pkg/model/personal.go`：`Personal` 加 `AvatarWidth/AvatarHeight int`（json: avatar_width/avatar_height, omitempty）。
- `resumeStore.ts`：加 `avatarRenderedSize`（`{width,height}|null`）+ `setAvatarRenderedSize`。
- `PreviewPanel.tsx`：分页后测量 `doc.querySelector('.r-avatar img')` 的 offsetWidth/offsetHeight 写入 store（无头像则置 null）。
- `PersonalSection.tsx`：`avatarW/H` 初始值与同步 effect 改为 `p.avatar_width ?? avatarRenderedSize?.width ?? 100`；`handleWidthChange/handleHeightChange/handlePresetChange` **总是同时写两个字段**，避免只写一个导致 `injectAvatarSizeCss` 的 `if(!w||!h)` 短路不生效。

**约定（长期）**：任何"编辑器 slider 的当前值"若需反映"模板默认渲染值"，一律通过预览 iframe 测量（offsetWidth/Height）回传 store，不硬编码像素、不解析模板 CSS。头像尺寸字段（avatar_width/height）必须两个一起写，否则注入函数因缺值而失效。

## 头像尺寸挤压 modern 模板 header 的布局修复

**背景**：modern 模板调大头像时，grid 第一行（text+avatar）行高被头像撑高，把第二行的 contact（邮箱/手机）推下去，且 text 下方留大片空白。第一次尝试用 `position:absolute` 让头像脱离 flow，但头像调大后会**盖住** contact，用户反对。

**最终方案（grid-template-areas，头像独占右列跨三行）**：所有「头像右置」单栏模板 header 统一为 `display:grid; grid-template-columns:1fr auto; grid-template-areas:"text avatar" / "contact avatar" / "langs avatar"`——头像独占右侧一列、跨 text/contact/langs 三行，文字/联系方式/语言全部排左列。这样头像调大（变高）只撑高右列，左列内容位置不变，**不会再把邮箱/手机等挤下去**，也不会盖住内容。

**改动范围**：5 个模板 CSS（compact/gradient/minimal/swiss/terminal）从 `"contact contact" / "langs langs"` 改为 `"contact avatar" / "langs avatar"`；bold、modern 用户已自行改好。同步更新模板契约文档 4 处：`templates/AGENTS.md`、`gosume-template-skills/SKILL.md`、`references/style-guide.md`、`assets/starter/styles.css`（头像右置的 areas 字符串 + 左置对称描述）。

**约定（长期）**：单栏模板 header「头像右置」的权威 grid 结构是 `grid-template-areas: "text avatar" "contact avatar" "langs avatar"`（头像独占右列跨三行，**不是** `"contact contact" "langs langs"` 的横跨整行形式）。不要用 `position:absolute`（头像调大必盖住），也不要另造 float 布局。头像居中/在上的模板（academic/classic/ink/leaf/executive/zen/timeline）是 `"avatar" "text" "contact" "langs"` 单列结构，不受影响。

## 修复：个人信息区 GitHub/LinkedIn 未渲染

**根因**：前端 `templateEngine.ts` 的 `snakeToPascal()` 做 snake_case→PascalCase 时，缺 `Github→GitHub`、`Linkedin→LinkedIn` 的首字母缩写修正。导致 `personal.github` → `Github`（H 未大写），而 template.html 用 `.Personal.GitHub`（与 Go 后端 `model.Personal.GitHub` 一致）访问不到 → `{{if .Personal.GitHub}}` 恒 false → 不渲染。`linkedin` 同理。

**修复**：`snakeToPascal` 的 replace 链补 `.replace(/\bGithub\b/g,'GitHub').replace(/\bLinkedin\b/g,'LinkedIn')`（已有 Id/Url/Qq/Gpa/Pdf/Png 的缩写修正）。

**约定（长期）**：模板字段名若有「驼峰内连续大写」的首字母缩写（GitHub、LinkedIn、ID、URL、QQ、GPA、PDF、PNG…），`snakeToPascal` 必须逐一手动补 replace 修正，否则前端 toGoShape 生成的名字与 Go 后端结构体字段名（以及 template.html 的 `.Field`）不一致，导致字段静默不渲染。新增这类字段时先确认 Go 结构体字段名大小写，再决定是否要补缩写修正。

## 修复：WelcomePage 模板卡片全部显示 loading 转圈

**根因**：Wails 模式下 `loadTemplateContent` 优先调后端 `TemplateService.GetTemplateContent`。若后端返回空/失败，fallback 到前端的 `templateMap`（`import.meta.glob` 内联的内置模板）。在某种条件下（可能是构建缓存、后端瞬时不可用、或前端 bundle 内 `templateMap` 为空），fallback 全部失败 → `tmpl.html = ''` → `renderTemplate` 返回空字符串 → `previewHtmls[id] = ''` → TemplateCard `{previewHtml ? <iframe> : <loading>}` 永远显示 loading 转圈。`templates` 列表仍能加载（`loadTemplateMetas` 走 Wails），所以卡片标题显示，只是预览区空白。

**修复**：
1. `services/templateService.ts` 的 `loadTemplateContent` 末尾加 **template.html 兜底**：当 `templateMap` 完全为空时，直接返回 `{ html: unifiedHtml, css: '', paperSize: 'A4', orientation: 'portrait' }`，确保 `previewHtml` 永远非空（template.html 由顶部 `import.meta.glob` 加载，比 `templateMap` 更稳）。
2. `WelcomePage` 的 `TemplateCard` 增加 `thumb?: string` prop：previewHtml 为空时优先显示 thumbnailService 的缩略图（dataURL），都没有则显示「暂无预览」文字（**不再无限 loading**）。父组件从 `useTemplateStore` 订阅 `thumbnails[tmpl.id]` 传入。

**约定（长期）**：`loadTemplateContent` 必须有「永远非空」兜底链：Wails 后端 → 内置 `templateMap` → 内置 `template.html` → `{ html: '' }`。任何一个环节失败都会导致 previewHtmls 为空、TemplateCard 无限 loading——这是静默的 UI 故障，比白屏更难发现。TemplateCard 也不应有「永远显示 loading」的分支：previewHtml 空时必须降级到 thumbnailService 缩略图或明确文字提示，不能无限旋转。
